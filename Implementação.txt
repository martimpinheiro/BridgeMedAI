Tabelas base de dados:
- documents: Documento que vamos aceder para procurar: MDR / IA ACT
- document_sections: Partes do documento: artigo x, capitulo y, anexo z
- document_chunks: pequenos pedaços que o chat bot vai ler, pois não vai ler os pdf inteiros 
- ingestion_jobs: quando o sistema processar o documento queremos saber quando acabou e quando acabou assim como se tudo correu bem e não ocorreu nenhum erro


Instalar os requirements: pip install -r Backend/requirements.txt
Para que cada coisa serve:
- chromadb: Serve para a base vetorial local. É o que usamos para guardar e consultar chunks com embeddings quando trabalhamos com a collection regulations_chunks
- pyodbc: Serve para ligar ao SQL Server. O código usa isto para ler e escrever nas tabelas da base de dados, como documentos, secções e chunks
- pymupdf: Serve para abrir PDFs e extrair texto. 
- python-dotenv: Serve para carregar automaticamente as variáveis do ficheiro .env, como DB_SERVER, OLLAMA_HOST, OLLAMA_CHAT_MODEL, EMBEDDINGS_PATH, etc
- fastapi: Serve para criar a API backend. É o que define os endpoints /health, /search e /chat
- uvicorn: Serve para correr a app FastAPI localmente. Ou seja, é o servidor ASGI que normalmente arranca a API com um comando tipo uvicorn api_main:app --reload
- pydantic: Serve para validar os dados de entrada e saída da API. No código é usado nos modelos QuestionRequest, SourceItem, SearchResponse e ChatResponse
- numpy: Serve para trabalhar com vetores e matrizes de embeddings. Usamos isto para calcular similaridade entre a pergunta e os chunks, normalizar embeddings e fazer ranking dos resultados
- ollama: Serve para falar com o Ollama a partir de Python. É ele que gera embeddings e respostas de chat no pipeline RAG

Backend:

api_main.py: porta de entrada do backend FastAPI. Tem três Endpoints: /health, /search e /chat. O /search chama search_question e o /chat chama answer_question. 

api_rag_service.py: Contém a lógica do chat. Tem as regras obrigatórias que o chatbot tem que cumprir assim como estabelece objetivos para a resposta, como por exemplo apresentar as citações. Faz com que não haja alucinações por parte do chatbot. Basicamente melhora a precisão da resposta. 

rag_router_utils.py: normaliza texto, extrai keywords, calcula similaridade por embeddings, valida o ficheiro local de embeddings, deteta o perfil do dispositivo, infere a intenção da pergunta, decide quais documentos alvo interessam, cria variantes da query para melhorar recuperação. Este ficheiro é que decide o que procurar antes de responder. 

regulations_and_WriteInTables.py: Transforma os ficheiros PDF de regulamentação em dados úteis para o sistema. Este ficheiro: lê variáveis do .env, liga ao SQL Server, calcula hash do ficheiro, extrai o texto de cada página, normaliza linhas e blocos, deteta cabeçalhos como capítulo, artigo e anexo, divide o documento em secções, tenta dividir secções mais longas em subunidades para ser mais fácil encontrar o que desejamos, parte o texto em chunks, constrói citações e grava documentos, secções, chunks e jobs de ingestão na base de dados.

export_embeddings_local.py: vai buscar os chunks à base de dados, calcula embeddings com o Ollama, e guarda tudo no ficheiro local_embeddings.pkl com records e embeddings. Esta uma solução sem usar o ChromaDB pois não estava a conseguir implementar

embed_chunks_to_chroma_local.py: faz algo parecido, mas em vez de guardar no ficheiro .pkl, envia os embeddings para uma collection do ChromaDB, com metadados por chunk. É o caminho “vector DB”. Quando colocarmos isto a usar vamos precisar de fazer alterações e melhorar a parte da pesquisa. 

search_embeddings_local.py: usa o ficheiro.pkl de embeddings locais, coloca a pergunta numa espécie de filtro para encontrar a melhor resposta e imprime os melhores resultados, com score, documento, secção e citação. O score basicamente vai classificar a documentação encontrada (artigos, secções, etc) de acordo com a pergunta que fizemos, quanto mais próximo de 1, melhor será para responder e o sistema irá basear-se nos artigos de lei que tiverem maior pontuação. 

search_chroma_local.py: faz pesquisa semântica diretamente na collection do ChromaDB. Como o ChromaDB não se encontra implementado, ou seja o vector Store, depois mais uma vez temos que melhorar isto quando estiver a funcionar. 

chat_rag_local.py: cria embedding da pergunta, pesquisa no Chroma, monta contexto, envia isso ao modelo de chat local, imprime a resposta.

chat_rag_local_no_chroma.py: versão mais trabalhada do chat sem ChromaDB, usando embeddings locais e regras mais fortes de citação e seleção de fontes. Está mais alinhado com o objetivo regulatório do projeto. Como escrevi em cima nas notas, depois podemos usar este ficheiro quando  implementarmos o ChromaDB pois já temos bastantes regras definidas. 

reset_chroma_db.py: faz reset global do Chroma persistente.

reset_chroma_collection.py: apaga apenas a collection regulations_chunks.

test_ollama_local.py: confirma se os modelos de embedding e chat do Ollama estão a responder.
